# 实验 055 · 本地 4B 能否补上规则找备用路线的缺口（离线，GPU）

2026-11-16 登记。分支 `route-discovery-neighbours`。状态：**预登记，探索性**。CPU 准备在本地完成，GPU 运行由用户在 LabServer 执行。

## 1. 背景与问题

选题：工具失败后自动发现备用路线，替代 BTM 的人工替代映射，再与 ACV 结合选路线（用户 2026-11-16 确认）。三个 Gate 的结果见实验 054 第 8 节：

- 原生 ToolMaze 给 Agent 的工具列表就是有效路径并集，路线发现要在加入同领域干扰工具的设定下做。
- 干扰设定下，C3（多步对多步）规则方法只找回约四成到六成；人工映射按构造是全对。

**问题：** 在同一干扰设定下，本地 Qwen3-4B 能否比规则多找回至少 10 个百分点的备用路线？

## 2. 设定

- **任务：** ToolMaze C3 全部 100 个任务（Hugging Face `dongsheng/ToolMaze`，每个基础任务取 P0 文件），每个任务两条有效路径，每条的差异段各当一次“失败路线”，共 200 个查询。
- **工具池：** 任务的有效路径工具 + 任务所属领域和 General 的全部工具（中位 92 个）。领域标签只用于构造工具池，模型和规则都看不到。
- **模型可见：** 任务原文（user_input.query）、失败路线的工具名，以及工具池中工具的公开合同（说明、参数及说明、返回字段）。不可见：`substitutes`、`alternatives.yaml`、`valid_paths`、领域和类别标签、插件代码。
- **划分：** 按实验 054 的备用组划分。查询的真值组属于 054 测试半边的记为测试集，其余为开发集。

## 3. 对照组

| 组 | 做法 |
| --- | --- |
| B1 规则 | 054 的“输入能接上”，搜索宽度 200，加“参数说明点名来源工具即可接整个返回”规则（见第 7 节），取前 3 |
| L 模型重排 | 规则生成器给出最多 20 条候选（B1 与义务匹配两种排序交替合并），模型按“是否完成同一部分任务”排序 |
| P 模型提出 | 不给候选，模型直接从工具池（去掉失败路线的工具）提出最多 3 条路线 |

**模型与采样：** Qwen3-4B-Thinking-2507（revision 768f209d），LabServer 本地 vLLM（ToolMaze 原服务脚本，32768 上下文，推理内容单独解析）。temperature 0.6、top_p 0.95、top_k 20、max_tokens 8192、种子 550001，单请求超时 600 秒。每个查询每组只调用一次，不重试、不替补；请求报错记为无效回答。提示词全文见 `extensions/toolmaze_recovery/route_judge.py`，在看到任何模型输出前冻结。

## 4. 假设、竞争解释与判据

- **H1：** 模型能理解“完成同一部分任务”，在测试集 C3 上比规则多找回至少 10 个百分点。
- **竞争解释：**
  1. **候选上限。** L 只能在规则候选里挑，开发集上候选上限约 0.69（前 20），L 的收益有天花板；P 不受此限，但要在约 90 个工具里自己拼链。
  2. **4B 能力不足。** 长提示（P 组约 90 个工具说明）可能超出 4B 的有效理解；单独报告无效回答率。
  3. **真值不全。** 真值每组只有两条路线，模型提出的其他合理路线会被判错，所有组同样受影响。

**主指标：** 测试集 C3 的 Recall@3（前 3 条中至少一条与真值逐步一致，评分允许 `substitutes` 等价替换）。

- **有效性前提：** L、P 两组请求报错率都不超过 5%，否则记为 `invalid_request_errors`，只报告。
- **继续（Go）：** max(L, P) − B1 ≥ 10 个百分点。
- **放弃（No-Go）：** max(L, P) − B1 < 5 个百分点。此时 4B 不足以做义务判断，下一步改用 API 模型或加入历史，不在 4B 上继续调提示。
- **其余：** 不确定，交给用户判断。

**次要指标：** Recall@1；开发集同样指标；候选上限；无效回答率；每次请求的输入、输出 Token。

## 5. 不在本实验内

- 与 Agent 的完整恢复和 BTM 的比较：本实验 Go 后另行登记。
- ACV 选路线：路线表可用之后再接入。

## 6. 运行

在 LabServer 干净检出本登记提交，确认 `benchmarks/ToolMaze/data/perturbed_tasks/c3` 存在，然后：

```bash
bash scripts/run_route_judge.sh
```

脚本先跑 CPU 测试，启动专用 vLLM，跑完 400 次请求（200 查询 × 2 组），结果写入 `results/055-route-judge-01/`（freeze、逐条回答、summary）。预计 2–3 小时（服务最多并发 2 条）。

## 7. CPU 准备与开发期记录

- **代码：** `route_judge.py`（提示、解析、评分、判据、运行器）；`route_discovery.py` 新增 `candidates()` 与“参数说明点名来源工具”规则，并修正名称遮蔽变体（说明中提到的其他工具名此前未遮蔽）。
- **提示长度（看到任何模型输出前调整）：** 200 个查询中测试半边 102、开发半边 98。P 组工具池最大 196 个工具，完整说明的提示最长约 9.1 万字符，加上输出可能超过 32768 上下文；P 组改用精简说明（说明前 200 字、参数名、返回字段），最长约 7.0 万字符（约 1.7–2 万 token）。另按“3 字符 1 token、留 512”给每次请求设输出上限（不超过 8192），保证不超上下文。L 组提示最长约 1.5 万字符。
- **测试：** `tests/test_route_judge.py` 5 项（提示只含公开合同、失败工具不在可用列表、解析与无效回答、假客户端端到端评分、请求报错使判据无效、C3 干扰池候选生成），连同 054 的 11 项全部通过。
- **开发期观察（开发集 C3，干扰池）：** 搜索宽度 40 时候选上限（前 20）0.60，B1 前 3 为 0.50；宽度 200 并加新规则后上限 0.69，B1 前 3 为 0.58。剩余漏检集中在几个购物推荐下单组。
- **如实说明：**
  - 诊断漏检原因时打印过 6 个 C3 样本，未区分开发和测试半边；据此加入的“参数说明点名来源工具”是通用合同规则，不针对具体组。
  - 登记前已在全部 C3（含测试半边）上算过规则分数和候选上限：054 第 8.2 节（宽度 40，B1 前 3 为 0.40）；按半边的候选检查（宽度 40，测试半边前 30 候选上限 0.66）；宽度 200 时全部 C3 的候选上限 0.725（新规则加入前）。规则是基线，这些数字没有用来选择模型组的任何设置。
  - 模型分数在登记前未计算，提示词未在任何模型输出上调整过。

## 7b. 运行前补充（2026-11-16，不改代码、判据和提示）

- **合同条件：** 工具说明取 Function Calling 说明加 MCP 的说明与返回字段。原生 Function Calling 说明只有 4/270 个工具写全返回字段、194 个完全没写，所以本实验属于“MCP 文档条件”，不等于原生 Agent 的视图。“只有原生合同、返回字段靠历史调用或试探来学”作为后续条件另行登记。

- **评分：** 主指标仍为严格匹配真值序列。全部回答保存在 `responses.jsonl`，义务等价的复核（试执行、隐去来源的人工标注）跑完后再登记规则补做，不重跑模型。
