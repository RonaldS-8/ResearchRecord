## 与当前暂停规则的关系

用户已要求：拿到真实 Agent 的失败归因之前，不批准新的核心数学方法，也不为方法定制 Benchmark。本实验两者都不涉及：

- 不新增估值、信念或学习方法；改变的是 Agent 与工具的**交互协议**：逐步调用改为一次写程序。
- 任务、工具合同、故障条件、计费和 scorer 全部原样复用，不新增任务或故障。

它仍是一条新的方法探索线，按 AGENTS.md 第 2 节，正式实验与 GPU 运行须先获批准。

## 动机与最近邻（对话中的文献检索，摘要级核对）

- 现有恢复工作（ToolMaze、Bench2Robust）都是**逐步反应**：每次故障都回到模型再推理一轮。
- 程序化工具调用（2608.06370 等）证明代码调用可减少模型往返，但没有在受控故障下研究“模型自己写的异常处理”。
- 带备用分支的计划（2509.08646）只是设计指南；自愈路由（2603.01548）的备用图由人工搭建，不是模型生成。
- 我们自己的记录里，逐步模式的损失多出在执行层：过早停止、不遵从建议、参数抄写错误（P05 漏句点）。程序按引用绑定参数（`content=record["summary"]`），抄写类错误在结构上不会发生；这是需要 GPU 检验的机制假设，CPU 不能证明。

## 程序接口

模型只写一段 Python 程序，可用三个函数：

- `call(tool, **arguments)`：执行一个已公开的工具，返回其 JSON 结果；工具失败以 `{"error": ...}` 返回，不抛异常。
- `finish(answer)`：以最终答复结束；无法完成时答复以 `Blocked:` 开头。
- `escalate(reason)`：结束程序，交回逐步 Agent 续做，续程能看到程序已做的全部调用。

执行器用语法白名单限制程序：禁止 import、下划线开头的名字和属性、未列出的属性方法、裸 `except`；只提供少量内建函数。行数上限防死循环，调用上限沿用会话的 16 次。程序拿不到 session、故障类型、费用或 scorer。

## CPU 部分（本轮运行）

**科学问题：** 在现有 38 个开发单元格（6 任务 × 各自登记的故障条件）上，程序接口能否表达完整恢复？无故障处理的程序会在多少单元格失败？

**参考程序：** 每个任务两段程序，见 `contingency_cpu.py`，运行前冻结：

- `contingency`：读失败超时重试一次再换备用源；非幂等写入结果未知时先查询再决定是否重写；凭据过期则刷新；无路可走或审批被拒时以 `Blocked:` 停止。
- `happy_path`：同样的任务逻辑及任务文本中写明的条件判断（如“若审批通过”），不处理任何工具错误，遇错即 escalate。

**H1（可表达性）：** `contingency` 程序在全部 38 格达到登记的预期结果：`blocked`、`backup_unavailable`、`authorization_denied` 三类为正确停止，其余为严格完成；非法调用为 0。
- 竞争解释：恢复需要程序无法写死的信息（如只能靠理解自由文本才能纠正的错误），使一次写成的程序有结构性上限。
- 证伪：任一单元格未达预期即 H1 不成立，如实记为负结果；不得改程序后当作同一轮结果。

**H2（故障有区分度）：** `happy_path` 程序恰好在 7 格达到预期：6 个 clean 格，加 `facility-access/authorization_denied`（拒绝是任务写明的业务结果，不是工具故障）；其余 31 格全部 escalate。
- 竞争解释：故障太温和，无处理的程序也能通过，则这些单元格无法区分程序质量。
- 证伪：达标格数不等于 7。

**余量记账（不是假设检验，是恒等式）：**

- 逐步执行同样动作所需的模型决策数 = 工具调用数 + 1（最终答复）。
- 完整程序的模型决策数 = 1。
- `happy_path` + 逐步续程的决策数下界 = 1 + （参考程序剩余调用数）+ 1。只在两段程序到升级点之前的调用序列完全一致时成立，执行时逐格核对，不一致记为不可计算。

**本轮 CPU 结果不能说明的事：**

- 参考程序的作者读过模拟器源码。它们只证明接口**能**表达，不证明仅凭公开合同**能**写出，更不证明 4B 模型能写出。
- 决策数不等于 Token 或时延；程序一次输出更长，Token 是否净省只能在 GPU 上测。
- 这是开发单元格，不是留出评测。

**Go/No-Go：** H1 成立且前缀核对全部一致，才建议申请 GPU 小样本；H1 不成立则先分析失败格，不申请 GPU。

运行命令（本地，结果不入 Git，摘要复制到 `docs/evidence/cp01/`）：

```bash
python -m extensions.toolmaze_recovery.contingency_cpu --out results/cp01-cpu-01
```

## GPU 部分（只登记，等待批准，本轮不运行）

**问题：** Qwen3-4B-Thinking-2507 能否仅凭公开任务与合同写出可执行的恢复程序？与逐步 ReAct 相比，严格完成是否持平，模型请求、Token 与时延是否下降？

**两组，同一 38 格，各 1 回合，共 76 回合：**

- ReAct：原样复用 `python -m extensions.toolmaze_recovery.run --task T --condition C --out ...`（full 模式、react 组），与以往 Gate 同一协议。
- Program：`python -m extensions.toolmaze_recovery.contingency --task T --condition C --out ...`。第一次请求不提供工具、只要求写程序；程序 finish 即结束；若 escalate、崩溃、无代码、被白名单拒绝或无 finish，则由原生逐步 Agent 带回放续做，总请求仍 ≤12。

**设置：** 与 `run.smoke` 相同：Qwen3-4B-Thinking-2507（revision `768f209d…`），vLLM 0.31.0，温度 0，SDK seed 2701，输出上限 6144，每回合 ≤12 请求，工具调用 ≤16。上限：ReAct ≤456、Program ≤456 请求，实际预计远低于上限。

**混杂：** 两组系统提示必然不同（协议不同）。比较的是“协议 + 其说明”的整体效果，不能单独归因于协议。

**指标（分项报告，不合成单一分数）：** 预期结果达成数（严格完成/正确停止）、非法调用、工具费与诊断费、模型请求数、输入/输出 Token、模型秒数；Program 组另报程序状态分布（finished/escalated/crashed/rejected/no_program/no_finish）、`finish_reason=length` 次数、按引用绑定与抄写绑定的逐例标注。

**预登记判据（单种子、开发集，只作方向筛查，不宣称显著性）：**

- 继续：Program 组达成数 ≥ ReAct 组 − 2，且每回合模型请求中位数下降 ≥50%，且总输入 Token 下降 ≥30%。
- 停止：程序可执行率（finished + escalated）低于 50%，说明 4B 模型写不出可用程序；或达成数比 ReAct 少 3 格以上。
- 介于两者之间：报告逐格差异，与用户讨论，不改条件补跑。

**已知风险：** 思考模型可能在 6144 输出内用完 Token 而没写出程序；按失败记录，不调大上限补跑。

## 结果（CPU，`cp01-cpu-01`）

运行于预登记提交 `5144f597cef5f662775ffa0bb377c20f6808397c`，工作区无未提交改动；本地 Python 3.14，代码已按 3.10 语法检查。原始输出在本地 `results/cp01-cpu-01/`，副本见 [summary.json](../evidence/cp01/summary.json)（SHA256 `530dadb0…72b1`）与 [cells.json](../evidence/cp01/cells.json)（`717e9735…50e7`）。一次运行，无重跑，未改程序。

**观察：**

| | 达到预期 | 非法调用 | 工具费 + 诊断费 | 模型决策数 |
| :--- | :--- | :--- | :--- | :--- |
| contingency 程序 | 38/38 | 0 | 159 + 4 | 38（每格 1） |
| 同样动作逐步执行 | 38/38 | 0 | 159 + 4 | 201（每格平均 5.3） |
| happy_path 程序单独 | 7/38 | 0 | 62 + 0 | 38 |
| happy_path + 逐步续程（下界） | — | — | — | 170（每格平均 4.5） |

- **H1 成立：** 38 格全部达到预期，正确停止的 6 格与严格完成的 32 格均通过原 scorer。
- **H2 成立：** happy_path 恰好 7 格达标（6 个 clean 格加 authorization_denied），其余 31 格全部 escalate。
- **前缀核对：** 31 个升级格中，两段程序在升级点之前的调用序列全部一致，下界可计算。

**解释（机制层面，非贡献）：**

- 只写主路径的程序几乎省不了决策：读取故障发生在第一个调用，升级后续程要做的事与逐步执行一样多。170 对 201 的节省全部来自写入故障和凭据过期这类发生在后期的故障。
- 省下决策要靠程序**事先写好处理分支**。这正是方向成立与否的关键：4B 模型能否写出这些分支。
- persistent 格比知道故障类型的参照多 1 次调用（先重试再切换）。逐步策略面对同样的公开信息也要付这一次，所以不影响程序与逐步之间的比较。
- 每格平均 5.3 次决策，与实验 038 真实 ReAct 回合的约 5.2 个请求/回合量级一致（不同夹具，仅作量级参照）。

**判断：** 按预登记，H1 成立且前缀全部一致，**CPU Go，建议申请 GPU 小样本**。CPU 只证明接口能表达完整恢复、且故障能区分有无处理分支的程序；不证明模型能写出，不证明 Token 或时延净省。
