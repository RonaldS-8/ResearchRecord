# 实验 054 · 从工具合同自动找回备用路线（CPU 召回检查）

2026-11-16 登记。分支 `route-discovery-neighbours`。状态：**预登记，探索性，仅 CPU**。不调用模型，不用 GPU。

方向依据：近邻对照见 `docs/reviews/053-route-discovery-neighbours.md`。用户决定先沿“恢复时的备用路线自动发现”推进，并与 ACV 结合；改研究目标需导师确认，本实验不改 AGENTS.md。

## 1. 问题

工具失败后，只用 Agent 可见的工具合同（名称、说明、参数、输出字段）和任务输入，能否自动找回 ToolMaze 人工标注的备用路线？

这是整条线的第一道门槛。整体目标是：自动生成的路线表在真实 Agent 上达到 BTM 人工替代映射的水平（以 BTM 静态规则为上限）。如果合同层面都找不回人工映射，就不必跑 Agent。

## 2. 数据与真值

- **工具合同：** `benchmarks/ToolMaze/tools/definitions/{source,processor,action}.yaml`，共 270 个工具，全部有输出字段说明。
- **真值：** `benchmarks/ToolMaze/tools/definitions/alternatives.yaml` 的 126 个备用组（一对一 44、一对多 34、多对多 48），每组 2 条路线，共 252 条，路线长 1–6 步。
- **查询：** 每条路线各当一次“失败路线”，要求找回同组的另一条，共 252 个查询。

**推导器可见（与 Agent 可见内容一致）：**
- 每个工具的 `name`、function_call 的 `description` 与 `parameters`（含类型、枚举、说明）、mcp 的 `prompt_description` 与 `output_schema`。
- 失败路线的工具序列，以及该组的任务输入参数名（路线里非 `$` 引用、非常量的参数）。

**推导器禁止读取（真值或非公开信息）：** 工具定义里的 `substitutes`、`alternatives.yaml`、`domain`、`category`、`tools/plugins/` 实现代码。测试会检查推导器不读取这些字段。

**评分时的等价：** 候选路线与真值逐步相同才算命中；评分器（只有评分器）允许把某一步换成该工具 `substitutes` 中列出的工具，因为真值只列了每组两条路线，其他同功能提供方同样有效。

## 3. 划分

每类结构内，按 `sha256("054:" + alt_id)` 排序，前一半为开发集，后一半为测试集（63 组 / 63 组）。所有设计与调参只看开发集；冻结并提交后，测试集只运行一次。

## 4. 方法与对照

全部为规则方法，不调用 LLM。

| 组 | 做法 |
| --- | --- |
| B0 名称相似 | 只按工具名词元重合度给单个工具排序，只能给出单步路线 |
| B1 输入能接上 | In-N-Out 式：在 270 个工具上搜索最多 6 步的链，要求每一步的必填参数能由任务输入或前面步骤的输出满足；最后一步输出与失败路线的最后输出有任意重合即可 |
| D 义务匹配（本方法） | 在 B1 的可执行链上，再要求候选完成同一义务：最后一步的输出覆盖失败路线最后一步的关键输出字段，并按说明中的动作与对象词元相似度排序 |

“能满足”的参数匹配规则（同名、词元重合、说明重合、枚举可取常量）三组共用，只在开发集上确定。D 的打分细节同样只在开发集上确定。

## 5. 假设、竞争解释与判据

- **H1：** 公开合同足以找回人工备用路线，而且“义务匹配”比“只要能接上”更准。
- **竞争解释：**
  1. **名称太规整。** ToolMaze 工具名带提供方后缀（如 `get_weather_openweather`），名称相似可能就够了。B0 和第 7 节的名称遮蔽变体用来检验这一点。
  2. **只要能接上就够了。** 如果 B1 接近 D，“义务匹配”就没有增量，贡献只能落在已有的 In-N-Out 式连通性上。
  3. **多步路线根本找不全。** 多对多组按类别单独报告。

**判据（测试集，D 组）：**
- **继续（Go）：** Recall@3 ≥ 0.80，且多对多组 Recall@3 ≥ 0.60。
- **放弃（No-Go）：** Recall@3 < 0.50。
- **其余：** 不确定，交给用户和导师判断。
- **机制判断（单独报告，不改变上面的结论）：** D 比 B1 的 Recall@3 高不到 5 个百分点，并且每个查询的错误候选数也不更少时，记为“义务匹配无增量”。

**次要指标：** Recall@1、Recall@5；每个查询在接受阈值以上的错误候选数；按一对一、一对多、多对多分开；名称遮蔽变体（工具名换成无意义编号，说明不变）的 Recall@3，下降超过 20 个百分点时标记为“依赖命名”。

## 6. 不在本实验内

- **参数绑定是否正确：** 本实验只判断路线（工具序列）是否找对。
- **按故障区分路线是否有效、写入安全：** 053 的 (b)(c) 两项，需要历史和副作用语义，下一步再登记。
- **与 ACV 结合：** 路线表给出候选动作集合，ACV 用合法历史估计每条路线在当前故障下的完成概率与成本。在本实验 Go 之后另行登记。
- **真实 Agent 比较：** 自动路线表、BTM 人工映射、不给提示三组，非劣界 5 个百分点，另行登记。

## 7. 局限

- ToolMaze 的合同和备用组都由同一个生成流程产出，措辞可能比真实 API 规整。本实验 Go 也只说明在 ToolMaze 上可行，后续需要在 AppWorld 或真实 MCP 工具说明上检验。
- 真值只列每组两条路线，评分器用 `substitutes` 扩展等价，仍可能漏掉其他合理路线，导致错误候选数偏高。

## 8. 结果

### 8.1 开发集进展（2026-11-16，测试集未运行）

代码 `extensions/toolmaze_recovery/route_discovery.py`，测试 `tests/test_route_discovery.py`（9 项通过）。开发集 63 组、126 个查询：

| 组 | Recall@1 | Recall@3 | 多对多 | 一对多 | 一对一 | 每查询前 3 名中的错误候选 |
| --- | --- | --- | --- | --- | --- | --- |
| B0 名称相似 | 0.32 | 0.40 | 0.00 | 0.18 | 1.00 | 2.19 |
| B1 输入能接上 | 0.46 | 0.53 | 0.42 | 0.21 | 0.91 | 2.03 |
| D 义务匹配 | 0.42 | 0.48 | 0.33 | 0.12 | 0.91 | 2.06 |

**开发期改动：** 第一版 D 的 Recall@3 只有 0.09，原因是它最奖励“与失败路线末端相似”的候选，结果把失败路线加一步当作备用。加入“与失败路线共用工具”的惩罚（B1 与 D 共用，也用于束搜索排序）后得到上表。

**观察：**
- 一对一几乎都能找回，这部分名称相似就够，说明 ToolMaze 命名规整。
- D 在开发集上不比 B1 好，“义务匹配”目前没有增量。
- 未命中样本里有两类：
  - 参数匹配过松，拼出语义不通的链，例如用银行余额去发布券商台账；
  - 候选看起来合理但不在真值里，例如 `generate_invoice_from_cart`、`hold_best_recommendation → confirm_held_recommendation_order`。
  真值每组只有两条，后一类会被记为错误，第 7 节的局限在开发集上已经可见。
- 规则推导在多步路线上明显不足，继续手调规则有过拟合开发集的风险。

**状态：** 未冻结，测试集未运行。下一步方法选择交给用户决定。

### 8.2 原生任务核对（Gate A，2026-11-16，探索性）

数据：Hugging Face `dongsheng/ToolMaze`（用户授权下载，放在仓库外 `D:\users\018574\.toolmaze-data`，不入 Git）。每个基础任务取 P0 文件；C2、C3 各 100 个任务，每个任务两条有效路径，都能对应到 `alternatives.yaml` 的一个备用组。参数沿用 8.1 的开发集取值，未针对任务调整；任务里的备用组与开发集、测试集都有重合，所以本节只作环境核对，不进判据。运行：`python -m extensions.toolmaze_recovery.route_discovery --tasks <data> --pool visible|domain --out ...`，摘要见 `docs/evidence/054/native-tasks.json`。

**ToolMaze 给 Agent 的工具列表就是答案。** `evaluation/core/sandbox.py` 用全部有效路径上的工具构建工具定义。核对 400 个任务：可见工具恰好等于有效路径工具的并集（C2 中位 7 个，C3 中位 9 个，C4 中位 15 个，270 个工具中最多占 6%）。规则“备用路线 = 可见工具里不在失败路线上的工具”在 C2、C3 的 400 个查询上全部找回备用路线（工具集合层面）。原生设定下谈不上“发现”路线，Agent 失败只能来自没认出关系。

**加入同领域干扰工具后才有难度。** 把任务所属领域和 General 的全部工具加入候选（中位 92 个；领域标签只用于构造环境，推导器看不到）：

| 设定 | 组 | C2 Recall@3 | C3 Recall@3（全为多对多） |
| --- | --- | --- | --- |
| 原生可见（中位 7/9 个工具） | B0 名称相似 | 0.73 | 0.00 |
| | B1 输入能接上 | 0.70 | 0.66 |
| | D 义务匹配 | 0.72 | 0.68 |
| | 集合差规则 | 1.00 | 1.00 |
| 同领域干扰（中位 92 个工具） | B0 名称相似 | 0.68 | 0.00 |
| | B1 输入能接上 | 0.70 | 0.40 |
| | D 义务匹配 | 0.59 | 0.37 |
| | 集合差规则 | 0.00 | 0.00 |

**对后续设计的含义：**
- 和 BTM 比较时不能用原生工具列表，否则自动路线表可以靠集合差直接得到，人工映射也失去意义。主设定改为“原生任务 + 同领域干扰工具”，原生结果作为附带报告，并作为 Benchmark 审计发现写进论文。
- 干扰设定下 C3 规则方法只有 0.37–0.40，C2 的一对一主要靠名称，方法的空间在多步路线。8.1 的“输入泄漏”担心不成立：`target_currency` 等参数本来就写在任务的 user_input 里。
- 路线是否合法仍按真值组判定，真值不全的问题（8.1）在干扰设定下同样存在，需要执行检查或人工标注补齐后再冻结判据。
