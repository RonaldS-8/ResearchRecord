# 实验 050 · 丢回执场景下 BTM 是否失效（探索性筛查）

2026-11-15 登记。分支 `lost-receipt`，基于 `gate47-audit`（346f635）。状态：**预登记，探索性**。只做 CPU 准备，GPU 运行由用户执行。

本实验不改 AGENTS.md 的研究问题。Q2 方法线的止损结论见 `completion-headroom` 分支的 `docs/reviews/049-q2-stop-loss-decision.md`。本实验只为和导师讨论“以 BTM 的不足为切入点”这一备选方向提供证据。结果无论正负都保留。

## 1. 问题

Bench2Robust 的环境里，随机错误按构造都是暂态的（拆解见 `docs/reviews/041-bench2robust-teardown.md`）。在那里，“失败后至少重试一次”几乎总是对的。

但真实系统里存在另一种失败：写入超时，其实已经提交，只是回执丢了。写入端不去重时，盲目重试会产生重复副作用。

**问题：** 在这种场景下，带 BTM 提示的真实 Agent 会不会重复写入或耗光预算？一条由公开合同推出的“先核实再重写”提示，能否在严格完成率上明显超过 BTM？

## 2. 场景：检查点 M5

代码见 `extensions/toolmaze_recovery/gate50.py`。

**前缀**（外生，不是 Agent 的动作）：
1. 主读成功，返回 evidence_ref。
2. 用这条 evidence_ref 发布，返回超时 `Upstream request timed out.`。

**三个隐藏世界**，前缀完全相同，测试已核对 Agent 看到的视图逐字节一致：

| 世界 | 第一次发布的实际情况 | 之后再发布 |
| --- | --- | --- |
| C | 已提交，回执丢失 | 每次都提交一份新的，产生重复 |
| T | 未提交 | 第二次起正常提交 |
| P | 未提交 | 一直超时，都不提交 |

**公开合同**（Agent 可见）：
- 发布工具不幂等，每次被接受的调用都创建一份新发布，不检查已有发布。任务禁止重复发布。超时不说明是否已提交。
- 备用写入走 `prepare_alternate_publication` → `confirm_alternate_publication`，它是独立写入端，同样不检查其他写入端的发布。
- 新增只读查询 `list_record_publications`，列出这条记录已提交的发布，包括回执丢失的。它记为显式诊断，单独计费。
- 回读 `read_published_record` 接受来自写入回执或查询结果的 publication_id。

**价格与预算：**
- 每次调用 1 个单位，失败也收费。查询记入诊断费，其余记入执行费。
- 总预算 7 次调用，前缀用掉 2 次，剩 5 次。
- 最长的稳健路径是“查询 → prepare → confirm → 回读”，需要 4 次，所以留 1 次余量。M4 是零余量，只能检验第一步，这里避免了这个问题。

**严格完成**（独立评分器 `gate50.evaluate`）：
- 恰好一份发布。
- 来源是真实主读回执。
- 写入或准备/确认的边真实存在。
- 提交之后有一次真实回读。
- 零非法调用，在预算之内，有合法的最终回答。

## 3. CPU 参照（真实执行器上的脚本策略，确定性）

各列依次为：是否严格完成 / 发布份数 / 恢复段调用次数。数据由 `gate50.reference_table()` 生成，测试已锁定。

| 预算 5 | C | T | P | 三世界等权完成率 |
| --- | --- | --- | --- | --- |
| 先重试再切换（类 BTM） | 否 / 2 / 2 | 是 / 1 / 2 | 是 / 1 / 4 | 0.667 |
| 直接切换（类 BTM 去掉重试） | 否 / 2 / 3 | 是 / 1 / 3 | 是 / 1 / 3 | 0.667 |
| 先查询再重试 | 是 / 1 / 2 | 是 / 1 / 3 | 否 / 1 / 5（预算不够回读） | 0.667 |
| 先查询再切换 | 是 / 1 / 2 | 是 / 1 / 4 | 是 / 1 / 4 | 1.000 |
| 知道世界的 Oracle（仅作参照） | 是 / 1 / 2 | 是 / 1 / 2 | 是 / 1 / 3 | 1.000 |

**预算敏感性：**
- 预算 4：“先查询再切换”仍是 1.000，但没有余量。
- 预算 6：“先查询再重试”也达到 1.000。
- 两条类 BTM 顺序在三种预算下都是 0.667，因为 C 世界里必然产生重复。

**这张表说明的是设计，不是 Agent 行为。** 只有 Agent 真的不先查询就重写时，类 BTM 的损失才会出现。BTM 的约束里有“不可逆操作前从真实返回确认字段”，模型可能据此自己先查询。这正是本实验要检验的。

## 4. 对照组

四组共用同一任务、工具、价格、预算和前缀。提示以 `Recovery information:` 用户消息的形式，插在第一次请求之前，与 Gate44/45 的插入方式相同。测试已核对各组的消息前缀和工具定义逐字一致。

| 组 | 内容 | 字符数 |
| --- | --- | --- |
| R0 | 不给提示 | 0 |
| BTM | Gate44/45 冻结的 BTM 静态指导原文（附录 B.1 的三段 + “不重试已报不可用的工具”），加替代映射和均匀 Beta(1,1) 信念 | 1419 |
| BTM_NR | BTM 去掉“失败后至少重试一次”这一句，其余逐字相同 | 1321 |
| H | 知情提示：超时不说明是否已提交，写入不幂等；再写之前先查询；查到就回读结束；查不到就走备用写入 | 643 |

**公平性说明：**
- **BTM 用的是均匀信念，不是历史拟合的。** 这个新检查点没有合法历史，用均匀信念对应 Bench2Robust 消融里“静态结构加均匀信念”这一组。论文中这一组拿到了大部分提升（固定版 33.7，完整 BTM 37.8）。所以本实验检验的是 BTM 的静态结构，不是完整 BTM。
- **H 是人工按公开合同和预算算术写的强提示**，相当于知情参照或最强简单规则，**不是我们的方法**。如果 BTM 在这里输了，方法要贡献的是“自动推出 H 这类提示”，那是下一步，不在本实验内。
- BTM_NR 用来识别机制：如果差距来自“至少重试一次”这一句，BTM_NR 应接近 H；如果来自“没想到先查询”，BTM_NR 也会在 C 世界失败。

## 5. 假设与竞争解释

- **H1（BTM 有可利用的不足）：** 带 BTM 提示的 Agent 在 C 世界里重写，产生重复发布，或在 P 世界里耗光预算。H 比 BTM 的严格完成率高至少 10 个百分点。
- **H0（BTM 足够）：** 模型依据 BTM 的“不可逆操作前确认”约束或合同文字，自己先查询。H 与 BTM 的差小于 5 个百分点。

**竞争解释：**
1. **基础模型本身就不查询。** 这时 R0 和 BTM 一样失败，不足不是 BTM 特有的，但 BTM 也没修好它。按 BTM 与 R0 的差异单独报告。
2. **H 赢只是因为它针对场景写得更具体。** 这是预期内的。它说明“具体的恢复关系提示”比通用指导有效，与 Gate45 的观察一致；但方法贡献要靠自动生成，不能靠人工写。
3. **失败来自参数或格式错误，而不是决策。** 非法调用单独计数；参数错误导致的失败不计入机制份额。
4. **抽样噪声。** 每组每个世界只有 10 回合，见第 7 节。

## 6. 判据（运行前登记，分析代码 `gate50.summarize` 已按此实现并有测试）

**主指标：** 每组的严格完成率，按 C、T、P 三个世界等权平均。

- **有效性前提：** H 组主指标 ≥ 0.80。不满足时记为 `invalid_hint_not_executed`：4B 连明确提示都执行不了，比较不成立，只报告，不下结论。
- **继续（go）：** H − BTM ≥ 10 个百分点，并且 BTM 组的失败中至少一半是重复发布或预算耗尽。
- **放弃（no_go）：** H − BTM < 5 个百分点。
- **其余：** 不确定（inconclusive），交给用户和导师判断。

**次要指标**（只报告，不进判据）：
- BTM 与 BTM_NR、BTM 与 R0 的差。
- 每回合的查询次数。
- 恢复段的执行费和诊断费，分列。
- 每回合的输入和输出 Token。
- 非法调用数。

不把费用、Token 和完成率合成一个分数。

## 7. 运行配置与统计

- **模型：** Qwen3-4B-Thinking-2507，revision 768f209d，本地 vLLM，运行时锁定 Python 3.10.12、vllm 0.31.0、openai 3.42.0。
- **采样：** temperature 0.6、top_p 0.95、top_k 20、max_tokens 6144、单请求超时 120 秒、每回合最多 12 次请求。Gate45/47 用 temperature 0，每格只得到 1–2 条轨迹，无法估计比例；0.6/0.95/20 是该模型推荐的思考模式设置。
- **种子与计划：** 种子 500001–500010。4 组 × 3 个世界 × 10 个种子 = 120 回合，组和世界的顺序随种子轮换（`gate50.plan()`）。
- **协议停止：** 任何 SDK 或协议错误都停止整批，不替补回合。每回合都按真实参数独立重放评分，结果必须一致。
- **统计：** 每格报告 Wilson 95% 区间；H − BTM 报告格内重抽样的 bootstrap 95% 区间（2000 次，种子 500050）。

**样本量如实说明：** 每组 30 回合，区间半宽约 15–18 个百分点，只能看清很大的差异。本实验是筛查，判据用点估计加机制证据。如果结论是继续，需要另外登记、扩大任务后做确认性比较。

## 8. 局限

- 只有一个任务、一个检查点。“丢回执”是按 BTM 的盲点设计的场景，这是假设本身，不是偏袒。这类失败在真实系统里有多常见，本实验不测量。
- BTM 用均匀信念，没有历史统计部分，见第 4 节。
- 本地无法运行 `test_no_leakage.py`（需要云端 ToolMaze 数据），需要在云端运行。本地已运行：Gate 系列共 94 项测试，其中 Gate50 新增 14 项，全部通过。另有 1 项是已有的 Gate34B 测试，因为本机没有 vllm 包而报错，与本次改动无关。

## 9. CPU 准备与验证（已完成）

- **执行器、评分器、四组提示、运行器和登记分析：** `gate50.py`，测试见 `tests/test_toolmaze_gate50.py`（14 项）。
- **通过真实 Agent 循环（`run_episode` + 假 SDK）验证：**
  - C 世界“查询 → 回读”成功。
  - C 世界盲目重试产生 2 份发布、判失败；T 世界重试成功。
  - P 世界“查询 → 切换”成功。
  - 请求带上了登记的采样参数，没有强制工具；R0 没有提示消息。
- **全流程假运行：** 120 个计划回合用脚本策略跑通，并经过分析脚本，结果与第 3 节的 CPU 参照一致。假运行产物已删除，不入库。
- **变异检查：** 9 个故意植入的错误全部被测试发现：
  - C 世界不提交
  - 写入端去重
  - 不要求回读
  - 接受两份发布
  - 世界信息泄漏进视图
  - 消融组未删重试句
  - 采样参数丢失
  - T 世界重试失败
  - 查询不计诊断费
