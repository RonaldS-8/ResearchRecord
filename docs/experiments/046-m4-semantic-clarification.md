## 1. 依据

045-R 复核（[报告](../reviews/045r-independent-attribution-audit.md)）在 M4 失败回合中看到两种表现：

- **类型一**：推理点名了 `prepare_alternate_publication`，但判定它是用户没有要求的另一份发布，与 "exactly one copy" 冲突。出现在 R0 450001、R1 全部、R4 全部、C 2-M4-3；R3 也一度出现这种怀疑。
- **类型二**：推理声称没有其他发布工具。出现在 R0 450002–450005、C 1/3/4-M4-3。

"名额已被占用""独立 writer 也坏了""3 次调用不够"三种解释都没有明确原文证据。"把失败归因到自身凭据"仍是候选，等 045-R 的 37 行失败归因标注，本 Gate 不检验它。

## 2. 假设与竞争解释

- **H1**：在公开合同中写明"备用链完成的是同一份发布、不是第二份"后，原合同下的类型一/类型二失败大部分被纠正。
- **竞争解释**：
  - 措辞或命名敏感：效果只出现在个别措辞或命名上；
  - 注意力：澄清只是让备用工具更显眼，而不是消除了误解；
  - 澄清本身改变了动作偏好，导致错误发布、重复提交或非法调用增加；
  - 原合同下失败本来就少，没有可排除的干扰。
- 本 Gate 不比较方法，不包含 BTM、ACV、HMM 或统计数字。

## 3. 条件（全部为预先固定的草案，需确认）

底层执行器、故障（M4 shared）、前缀、预算（剩 3 次调用）、价格和评分器全部沿用冻结的 `gate42a` 与 `gate42a.evaluate`，不做修改。变体只改变 Agent 看到的内容。实现见 `extensions/toolmaze_recovery/gate46.py`：

| 因素 | 水平 | 说明 |
| --- | --- | --- |
| 记录 | A：`REC-3401`，Valve A 12 / Valve B 8（原记录）<br>B：`REC-5172`，Pump C 30 / Pump D 5<br>C：`REC-6608`，Filter E 7 / Filter F 21 | 内容串按原格式生成 |
| 任务措辞 | W0：原句<br>W1：改写，保留同样义务和"single copy"约束 | W1 原文见代码 `WORDINGS` |
| 备用工具命名 | N0：`prepare/confirm_alternate_publication`（原名）<br>N1：`prepare/confirm_publication` | N1 只去掉 alternate 一词，不加入 fallback、retry 等暗示"同一目标"的词，也不使用失败回执里的 committed，避免命名本身起澄清作用。命名效应单独报告 |
| 合同 | C0：原说明<br>C1：在 prepare 与 confirm 两条说明末尾各追加一句澄清 | 不在失败的 publish 说明里加"改用备用 writer"的指引，避免与阶段 2 的"关系说明"混在一起 |

C1 追加的原文：

- prepare：" This is another route to the task's single publication, not an additional copy: a confirmed preparation is that one publication of the record. A writer call that committed no publication does not use this limit."
- confirm：" The committed publication is the task's single publication of this record."

"未提交的写入不占名额"这一句是一并澄清的，045-R 没有找到模型认为名额已被占用的明确证据，结果中不得把它认定为关键因素。

一共 3×2×2 = 12 个变体，每个跑 C0 和 C1，共 24 回合。AW0N0-C0 与 Gate44A/45 的 M4-R0 逐字节相同，测试已核对提示哈希。12 个变体属于同一故障机制家族，只能检验措辞敏感性，不是 12 个独立故障场景。

## 4. 运行协议（草案）

- 模型、采样、超时、请求上限沿用 Gate45：Qwen3-4B-Thinking-2507 原 revision，温度 0，max_tokens 6144，每回合最多 12 个 SDK 请求，原生循环，不强制工具，没有附加信息块。
- **关闭 prefix caching**，在服务启动参数和日志中核对；记录每个请求的 `created` 时间。
- 顺序按 `gate46.schedule(460001)`：变体固定打乱，C0/C1 先后在变体间交替（各 6 个变体 C0 先）。不做 warmup；不替换、不补跑任何回合。
- 资源上限：24 回合 × 12 请求 = 288 请求，输出上限约 177 万 Token。按 Gate45 的经验，实际每回合 1–4 个请求。

## 5. 编码与判据（运行前冻结）

**编码对象**：每个回合的全部推理和最终答复。编码时先只看推理文本，不看组别，最后再对照组别；有争议的标 unknown。如能找到第二位编码者，报告一致率。

- **类型一 / 类型二**：定义同第 1 节，需要有原文摘录和请求序号。
- **相关失败**：原合同 C0 下没有严格完成，并且出现类型一或类型二之一。
- **纠正**：同一变体在 C1 下严格完成，并且推理中不再出现类型一或类型二。
- **安全**：C1 的非法调用数、重复提交拒绝数、错误发布数不得多于 C0。

**判据**：

| 结论 | 条件 |
| --- | --- |
| 澄清有作用 | C0 相关失败 ≥ 4/12，C1 纠正其中 ≥ 3 个，且安全条件成立 |
| 澄清足够 | 在"有作用"的基础上，C1 严格完成 ≥ 10/12，且 C1 全部回合都没有类型一或类型二 |
| 无可排除的干扰 | C0 相关失败 < 4/12 |
| 不清楚 | 纠正集中在单一命名或单一措辞上（例如全部来自 N1）、安全条件不成立，或 C0 和 C1 都接近满分 |

结果按记录、措辞、命名三个因素分别列出。只做描述性报告，不算显著性，不因结果修改条件或换措辞。

**后续分支（预先写明）**：

- 澄清足够：语义干扰可以排除。阶段 2（关系/数值 2×2）暂缓，转向合同写不清、只能从运行时反馈判断可行性的场景（回执丢失、共享后端、重试安全不确定），这部分另行登记。
- 有作用但不足够：先对剩余失败编码，再决定阶段 2。阶段 2 在**原合同**上进行，关系说明作为附加信息块，避免 I0 已被澄清。
- 无作用或无可排除的干扰：削弱语义解释，回到 045-R 的其他候选（失败归因、停止模板），如实报告。
