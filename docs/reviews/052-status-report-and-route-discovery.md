# 阶段报告：最新结果、路线自动发现方向与分支整理

2026-11-15。面向用户与导师讨论。只汇总已提交的记录，数字链接到原始实验文件。

## 一、结论

1. **止损建议暂停。** 049 的第一条理由（“简单规则已等于或接近最优”）被实验 048 第三轮推翻：前两轮的简单规则是按每个场景的真实参数挑的，对规则过于有利。
2. **“从历史估计场景再选策略”在 CPU 上通过登记判据（Go）**，但价值主要来自“估计场景”，不是“自适应规划”（实验 051）。
3. **只按回合成功率统计（BTM 式、ACV 首动作式）在 CPU 上比冻结规则还差**，说明要区分故障机制，而不是只数成功率。
4. **真实 Agent 的主要失败仍是认不出备用路线**（049 第二条理由不变）。BTM 靠人工给出替代映射来绕开这一点，这正是我们可以切入的地方：自动发现并验证备用路线。
5. 目前所有新结论都还是 CPU 结果，没有真实 Agent 证据，也没有在云端复跑。

## 二、最新结果

### 2.1 实验 048 第三轮：规则冻结后迁移（[第 9 节](../experiments/048-completion-headroom.md)）

规则表只按公开信息分组（剩余调用数、备用路线步数、首次报错类型）。规则在一部分场景上选好后冻结，再放到隐藏参数不同的场景上测试。表中数字是公共最优（按真实参数求解）多完成的百分点：

| 规则选法 | 中位数 | 差距 ≥10 的格 | 判定 |
| --- | ---: | ---: | --- |
| 冻结后迁移（登记的主判据） | 4.6 | **20.8%** | **有余量** |
| 一张表用于全部场景（样本内） | 3.8 | 8.9% | 局部余量 |
| 每个场景各自最优（前两轮的口径） | 0 | 0 | 局部余量 |

- 换场景后掉得最多的两种情况：首次报错信息量从大变小，以及备用路线从可靠变成不可靠。
- 完成率持平时，冻结规则多付费中位 23%。
- 第一轮网格（场景结构较简单）仍是局部余量。

### 2.2 实验 051：方法从历史估计场景能拿到多少（[实验 051](../experiments/051-history-estimated-recovery.md)）

每个场景给 N 条合法历史回合，比较四组：

- **FR 冻结规则**：设计者在其他场景上选好的规则表。
- **EMP 经验首动作**：只按日志计数选第一步。
- **HR 用估计结果选规则**：混合组，用方法的估计器在固定规则里挑。
- **M 方法**：先估计是哪类场景，再规划。

| 相对冻结规则（百分点） | N=10 | N=50（主） | N=200 |
| --- | ---: | ---: | ---: |
| 余量上界（公共最优 − FR） | 6.2 | 6.2 | 6.2 |
| **M − FR** | 1.4（No-Go） | **5.6（Go，18.9% 的格 ≥10）** | 6.2 |
| HR − FR | 2.1 | 4.9 | 5.4 |
| EMP − FR | −12.0 | −5.2 | −2.5 |
| M − HR（自适应规划的额外贡献） | −0.6 | 0.6 | 0.8 |

- **要多少历史：** 约 50 条历史时，方法收回余量上界的 90%；10 条不够。
- **对模型失配的稳健性：** 把真实场景从假设集合里去掉，结果几乎不变（5.4）。
- **收益来源：** 主要来自“估计场景”。在估计出的场景上挑固定规则（HR）已经接近方法本身，所以论文主张应写成“从历史估计故障机制，据此选择恢复策略”，而不是“精细规划”。
- **只数回合成功率不可靠：** 只按回合成功率挑首动作（EMP）比冻结规则还差。这一点直接指向 BTM 的统计部分：它记录的是“某工具出某错后回合最终成功的比例”，同样会被后续动作和小样本混淆。BTM 论文自己的消融也显示统计部分贡献很小。

### 2.3 仍然成立的旧结论

- **真实 Agent（Gate45/46/47）：**
  - 不给提示时，M4 检查点 0/5；给出“publish 失败可改走 prepare”的关系后 5/5。
  - 强模型没有可复现的“理解正确却选错动作”。
  - 合同澄清对 4B 的误读纠正为 0/12。
- **成本维度上界（实验 040/041）：** 相对较好固定规则最多省 7.5%–12.5%。这个上界同样是在“每格最优规则”口径下算的，按 048 第三轮的教训应当复核。

## 三、和 BTM 比：我们能主张什么

| 维度 | BTM | 我们 |
| --- | --- | --- |
| 备用路线从哪来 | 人工整理的替代映射写进提示 | 目标：从工具说明和历史调用里自动发现并验证（第四节） |
| 历史怎么用 | 按（工具, 错误）统计回合最终成功率，Beta 平滑 | 用历史估计故障机制（暂态 / 持续 / 共享后端 / 已生效丢回执），再选策略 |
| 成本与预算 | 不计工具费；“至少重试一次”是硬约束 | 工具费、诊断费分列；预算紧时不强制重试 |
| 不可逆副作用 | 写后检查返回是提示里的一条约束 | 写入超时后先核实再重写，避免重复副作用 |
| 证据 | 公开消融：静态结构贡献大，统计贡献小 | CPU：估计机制明显优于冻结规则，只数成功率反而更差 |

可写的主张草案：**在计费、有预算、可能丢回执的工具故障场景里，从合法历史估计故障机制并据此选择恢复策略，完成率高于设计者冻结的规则和只数成功率的统计；如果再能自动发现备用路线，就去掉了 BTM 对人工映射的依赖。** 第一部分有 CPU 证据，第二部分还没有任何证据。

## 四、方向：自动发现备用路线

### 4.1 为什么值得做

- **这是真实 Agent 的头号失败。** 4B 和 API 模型在 M4 上失败，都是因为没认出 prepare → confirm 这条备用链。一旦告知关系，就能完成。
- **BTM 绕开了这个问题。** 它的替代映射由人工写进提示，真实业务里没有人会提前写好每个工具的替代关系。如果我们能自动得到这张映射，并且达到给了人工映射的 BTM 的水平，这就是对 BTM 前提的直接改进。
- **CPU 结果说明路线知识之外仍有价值。** 知道路线之后，“怎么用历史选动作”还能多拿约 5 个百分点（051），两层可以叠加。

### 4.2 可能的做法（都还没实现）

1. **从工具合同推导。**
   - **按输出找输入：** 一个工具的输出字段能满足另一个工具的输入（例如 `pending_publication_ref` 只由 prepare 产生、只被 confirm 接受），由此拼出能完成同一义务的另一条链。
   - **按义务匹配：** 合同中写明“发布 / 记录 / 核验”等义务的工具，按义务归类。

   这一步只用公开说明，不读环境真值。
2. **从历史调用验证。** 推导出的候选路线，在历史里看是否真的完成过同一义务、成本多少，以及在哪类故障下有效。这和 051 的“估计故障机制”是同一套历史。
3. **交给 Agent 的形式。** 只给一张自动生成的“义务 → 可选路线 → 证据”表，替换 BTM 的人工映射，其余条件与 BTM 相同，形成对照。

### 4.3 怎么检验（建议的最小实验，待登记）

- **任务：** ToolMaze 现有 M3/M4，加上 `lost-receipt` 分支正在准备的丢回执检查点，再加 2–3 个路线结构不同的新检查点，避免只在一个检查点上调。
- **对照组：** 不给提示；BTM 加人工映射；自动映射；自动映射加历史估计。
- **判据草案：** 自动映射组的严格完成率不低于 BTM 加人工映射组 5 个百分点以上（非劣），且 Token 更少；自动映射加历史估计组优于 BTM。
- **先做 CPU 部分：** 写路线推导器，在现有检查点的工具合同上检查能否找回人工映射（召回率、误报）。这一步不需要 GPU，一两天可出结果。召回不了就不必跑 Agent。

### 4.4 风险

- **合同可能太规整。** ToolMaze 的合同是我们自己写的，路线关系可能写得过于明显，自动推导容易，泛化性会被质疑。需要措辞不同（Gate46 的中性命名就是这类变体）、结构不同的检查点。
- **能推导出路线不等于 Agent 会用。** Gate46 显示合同澄清对 4B 无效，自动映射也可能同样无效。所以真实 Agent 检验不能省。
- **BTM 没有开源。** BTM 是我们按附录 B.1 复现的，对比需要说明复现差异。
