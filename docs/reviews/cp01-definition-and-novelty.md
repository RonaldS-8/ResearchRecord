# cp01 预案式恢复：定义与创新性核查

2026-11-14，分支 `contingency-recovery`。按 AGENTS.md 科研原则 1（核对最近邻并说明区别）写成。文献核对多数只到摘要级，标注处读了正文或官方文档；检索不保证穷尽。

**结论先行：** 按 cp01 现在的形式，预案式恢复**不是方法创新**，而是现有几条线的组合：
- 模型先写计划或程序、执行器跑完：ReWOO、LLMCompiler、程序化工具调用；
- 偏离预期时交回模型重规划：AdaPlanner、LLMCompiler；
- 经典 AI 早就研究过“事先为哪些故障写分支”：增量与有限分支的条件规划。

cp01 的 CPU 结果本身也是一个恒等式，证明不了方法优势。它要成为硕士论文的实质贡献，必须换成下文第 4 节的问题。

## 1. 定义

沿用 AGENTS.md 的符号：$h$ 为 Agent 合法可见的任务、剩余义务与反馈历史，隐藏故障状态 $z$ 不可见。

**逐步恢复（现有做法）：** 每一步由模型 $M$ 根据当前历史选下一个动作，即 $a_t = M(h_t)$。每个动作对应一次模型请求。

**预案式恢复：** 在某个**编写点** $t_0$（任务开始，或首次故障后的恢复检查点），Agent 一次性写出程序 $\rho$。$\rho$ 是从 $t_0$ 之后的公开观测历史到下一个输出的确定性映射，输出只有三种：

$$
\rho(h_{t_0:t}) \in \{\text{工具调用}\} \cup \{\texttt{finish}(\text{答复})\} \cup \{\texttt{escalate}\}
$$

可信执行器只解释并执行 $\rho$：校验参数、计费、执行工具、记录回执。它不替 Agent 选动作，也不代办续程，这与 AGENTS.md 对执行器的要求一致。$\rho$ 输出 escalate、崩溃或无 finish 结束时，控制交回模型逐步续做，续程能看到 $\rho$ 已做的全部调用。

**覆盖率：** 对真实隐状态 $z$，$\rho$ 走到 finish 的历史为已覆盖分支，走到 escalate 的为未覆盖分支。覆盖率定义为

$$
\kappa(\rho)=P(\rho \text{ 以 finish 结束}\mid h_{t_0}).
$$

已覆盖分支也可能写错，例如结果未知时直接重写，造成重复副作用；这类错误须与“交回模型”分开计数，它比 escalate 更糟。

**与三类信息来源的对应（AGENTS.md 诊断定义）：**

- ① 已有反馈：编写时 Agent 只有合同和 $t_0$ 之前的历史。
- ② 显式诊断：程序里的付费查询分支，例如写入结果未知后先查询。仍单独计为诊断次数与诊断费。
- ③ 执行性信息：重试或切换的回执由程序自动消费。

与逐步恢复的唯一区别：**用不用某条信息、怎么用，在信息到达之前就决定了**（提前承诺），而不是到达之后再决定（延后决策）。

**价值口径：** 编写点的价值沿用 $Q^\pi$ 的二元形式，完成概率与成本分开报告：

$$
\bigl(P(\text{严格完成}\mid h_{t_0},\rho,\pi_{\text{续}}),\;\mathbb E[C_{\text{工具}}+C_{\text{诊断}}],\;\mathbb E[\text{模型请求、Token、时延}]\bigr)
$$

其中 $\pi_{\text{续}}$ 为 escalate 之后的模型续程策略。模型侧成本单列，不与模拟工具费相加。

**不是预案式恢复的情况：**

- 手写参考程序：作者知情，是知情参照，不是 Agent 结果。
- 外部规则替模型选动作：那是 Gate 33 的强制或建议干预，动作由外部控制器决定。
- 只写主路径、遇错即 escalate 的程序：它几乎不省决策（cp01 中 201 → 170），我们称之为“主路径程序”，作为对照。

## 2. cp01 CPU 结果说明了什么，没说明什么

任何只依赖公开历史的确定性逐步策略都能写成 $\rho$，反过来也成立。所以在理想策略层面，两者的工具结果与费用**完全相同**，cp01 的 38/38 与费用一致正是这个恒等式的实例。

预案式恢复与逐步恢复的差别**只可能**来自两处：

1. 每次决策的模型成本：请求数、Token、时延。
2. 模型在编写点与在运行时的**可靠性差异**：同一个模型，事先写分支和事后看到故障再选，哪个更容易选对。

第 1 点是程序化工具调用已证明的收益，不新。只有第 2 点可能是研究问题。

## 3. 最近邻与区别

| 工作 | 做了什么 | 与 cp01 的区别 |
| :--- | :--- | :--- |
| ReWOO（2305.18323，摘要已核） | 先写完整计划，用证据变量引用工具结果（按引用绑定），Token 省约 5 倍，称在工具失败下更稳健；把推理能力从 175B 迁移到 7B | 计划是线性的，没有故障分支；失败留给最后的汇总模块处理 |
| LLMCompiler（2312.04511，ICML 2024） | 规划器生成任务依赖图，执行器并行调用，中间结果可触发重规划 | 故障处理是事后重规划；目标是延迟与并行，不是故障恢复 |
| AdaPlanner（2305.16653，NeurIPS 2023） | 代码式计划，预测每步预期反馈；偏离预期时由模型改写计划并从中间续做 | **机制上最接近**“程序 + 交回模型”。区别：环境为 ALFWorld/MiniWoB；无工具故障谱系、无非幂等写入、无精确费用与严格验收 |
| CodeAct（2402.01030，ICML 2024） | 每步动作是代码，解释器报错作为下一步观测，模型自我调试 | 每步一次模型请求，本质仍是逐步反应 |
| 程序化工具调用（Anthropic 官方文档已读；OpenAI Agents SDK 同类功能） | 模型写代码调用工具，工具错误返回给代码，由代码处理 | 已是生产功能。官方文档把“每步依赖模型推理的严格顺序流程”和“调用少、结果小”列为**不适合**，这正是我们任务的形状；无受控故障评测 |
| 计划后执行指南（2509.08646） | 建议在初始计划里写入“工具 A 失败则用 B”的条件分支 | 设计指南，无实验 |
| 编译后执行（2605.14290，摘要） | 主张 Web Agent 先写程序再执行，动机是防注入；WebArena 81% 任务可用纯静态程序完成 | 动机是安全，不研究故障恢复与成本 |
| 自愈编排器（2606.01416，摘要） | 运行时按推断的故障类别选恢复动作，对比只重试和全量重规划 | 恢复在运行时选，未说明分支由谁事先编写；未报告模型调用成本 |
| 增量条件规划（Dearden 等，2003）；有限分支最优条件规划（Meuleau 与 Smith，2003） | 先有种子计划，再按期望效用决定在哪些点加故障分支；或在至多 k 个分支的限制下求最优 | **“事先为哪些故障写分支”这一问题本身已有经典研究**。差异：规划器是可靠的搜索算法；分支成本是计算量，不是模型请求；没有“规划器自身会出错”的问题 |

检索中**没找到**的（不等于不存在）：

- 同一个语言模型“事先写故障分支”与“事后反应”的受控对比；
- 涉及结果未知的非幂等写入，或凭据过期这类业务语义故障的预案评测；
- 小模型在编写点与运行时可靠性差异的测量。

## 4. 什么情况下才算贡献

**判断：** 若 GPU 只得出“4B 模型能写带异常处理的程序，所以省请求”，审稿人会认为这是程序化工具调用的已知收益加一个具体场景，属于“琐碎但没人显式写过”的工作。它可以作为论文的一节工程观察，撑不起核心章节。

可能构成实质贡献的只有下面两种，都需要另行登记和批准：

**A. 预判与反应的可靠性差异（实证型，新颖度中等）**

- 假设：同一个小模型，事先写分支比看到故障后再选更容易选对恢复动作。
- 与 Gate45 的联系：Gate45 的 18 个失败中，恢复决策占 16（提前停止 12、重读主工具耗光预算 4），逐字格式 1、漏回读 1；给出具体建议后模型能独立完成。预案式恢复相当于让模型在故障发生前**自己给出具体建议**；按引用绑定参数可在结构上消除逐字抄写错误；回读写在程序里就不会漏。
- 竞争解释：模型把同样的提前停止写进程序（直接 `finish("Blocked: ...")`），则没有收益；或预判的好处只来自“提示里提到了失败”，那么在逐步模式里加同样提醒也能获得同样收益。
- 必要对照：逐步 ReAct、逐步加“先想好失败怎么办”的提醒（剥离提示效应）、程序模式。没有中间这一组，就无法区分“提前承诺”与“提醒”。
- 必须覆盖 Gate45 失败集中的 M3/M4 检查点。cp01 目前 38 格都来自 `RecoverySession` 夹具，不含 M3/M4。

**B. 由不可靠模型编写的有限分支预案（方法型，新颖度较高）**

- 问题：在模型请求有成本、模型编写分支会出错的条件下，哪些故障分支值得事先写，哪些留给运行时。这是经典有限分支条件规划在语言模型 Agent 上的版本，与 AGENTS.md 的“信息价值看能否改善后续决策及总成本”同一思路。
- 风险：这是新的数学方法，属于当前暂停范围，须在 A 给出可靠性差异的证据之后、经批准才能做。没有 A 的差异，B 就没有可优化的对象。

**建议：** 先把 cp01 的 GPU 设计改为 A 的三组对照，并加入 M3/M4 检查点，作为修订预登记交用户批准。原 cp01 GPU 设计（两组、38 格）保留不删，未运行。若 A 不成立（三组无差异，或差异全由提醒组解释），预案式恢复只保留为工程观察，方向 No-Go。
