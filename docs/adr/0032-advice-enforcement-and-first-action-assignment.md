# ADR-0032 · 建议与强制分离、首动作分配

- 日期：2026-11-11
- 状态：已批准实现与 CPU 验收（用户 2026-11-11 批准 A–E 及三条附加要求）；模型回合按 [实验 035](../experiments/035-advice-enforcement-and-assignment.md) 由云端执行

Gate 33，在 `Dependence` 分支完成后提 PR。Q2、诊断定义与 $Q^\pi(h,a)$ 沿用 AGENTS.md，序贯检查点沿用 [ADR-0031](0031-sequential-recovery-decision.md)。

## 背景与问题

Gate 32 的规则组把工具列表删到只剩规则选中的工具，并在系统提示里加一句话，但没有约束模型必须调用它。`not_found` 回合里规则选了 `reserve_stock`，模型直接作答结束（[实验 034](../experiments/034-sequential-recovery-decision.md)）。这留下三个问题：

1. 这一组既不是“建议”（其他工具被删掉了），也不是“强制”（模型可以不调用）。它的失败说明不了规则本身够不够用。
2. “确认无记录之后重新预留”从未被真正执行过。$Q^\pi(h,\operatorname{do}(a))$ 需要动作确实发生，现有归档里这个动作的实得样本数是 0。
3. 规则和上下文重建写死了库存任务的字段，发布家族的同类义务无法复用；规则在查询失败一次后就停止，作为对照偏弱。

## 决策

**区分三种做法，分别归档，不混排。**

| 名称 | 工具列表 | 系统提示 | 是否约束调用 | 性质 |
| --- | --- | --- | --- | --- |
| `react` | 完整 | 无附加 | 否 | 模型自主选择 |
| `advice_only`（新增） | 完整 | 写明规则建议的工具，并说明由模型决定 | 否 | 建议式；记录模型是否照做 |
| `simple_feedback` | 只留规则选中的工具 | 写明规则选中的工具 | 是，请求带 `tool_choice` | 强制执行的规则基线 |

`simple_feedback` 自本轮起才是真正强制执行。Gate 32 的两个 `simple_feedback` 回合是“删工具但不强制”的旧条件，保留原记录，不与本轮合并统计。规则选择停止时不发强制请求，沿用原有做法。规则只定工具，参数、回执消费、后续步骤和最终答复仍由模型完成。

**首动作分配是工具层面的干预，不是一个参赛组。** 在登记的检查点阶段首次出现时，若分配的工具属于当前证据允许的动作，则该次模型请求带 `tool_choice` 指定它；之后各步由模型自主续程。归档分配的阶段与工具、分配方式与概率、模型实际调用的工具与参数、是否照分配调用、该调用是否被执行器接受。分配的工具不在证据允许集合内时不施加干预并如实记录。分配与实际不一致、或调用被拒绝的回合，不算该动作已执行。分配回合只能与 `react` 续程搭配，不与规则组叠加。

本轮采用逐一列举的同起点分支：每个登记的分支各跑一次，分配概率按设计为 1，归档中标为 `enumerated`。候选动作多到无法列举时再改为随机分配，届时另行登记。

**一次结果不是概率估计。** 检查点上各动作的完成率与剩余费用继续记为未知、支持度 0。分配回合的结果作为该分支的一次观察单独描述，不写入估值。

**上下文重建改为由合同描述。** 写入、查询、复核工具，标识字段，查询的作用域字段，写入实参与其证据来源，复核需吻合的字段与固定状态，义务文字，均从公开合同读取。库存合同的判定结果与原实现逐项一致；新增发布合同只用于 CPU 验证，本轮不在发布家族上跑模型。

**简单规则在查询失败后再查一次。** 连续两次查询失败才停止；其余选择不变。

涉及 `extensions/toolmaze_agent_recovery/methods.py`、`extensions/toolmaze_recovery/run.py`、`tests/test_toolmaze_sequential_recovery.py`，新增启动脚本 `scripts/run_gate33.sh`。不改公开工具合同、执行器、计价、评分、原生 Agent 和历史归档。无新增依赖。

## 备选与取舍

- **把规则组直接改成建议式。** 放弃。强制执行的简单规则是 AGENTS.md 要求的强基线；建议式回答的是另一个问题，即信息写进提示后模型是否采纳，这也是 BTM 和我们的估值最终要走的通道。两者都保留。
- **把强制执行当作我们方法的形式。** 不采用。研究对象是 Agent 自主选择恢复动作；每一步都被替换就不再是研究 Agent 的决策。强制只出现在规则基线和分配干预里。
- **再加一个强制参照组。** 用户确定本轮不加。
- **用提示措辞探针解释模型为何停止。** 用户确定暂缓，等云端整理出停止回合的推理原文再定。
- 代价：`simple_feedback` 的含义相对 Gate 32 变了，跨 Gate 不可直接比较；归档多了分配与遵从字段；规则多查一次会多付一次诊断费。

## 验证与边界

- 本机可验证：上下文、规则、请求中的 `tool_choice`、工具列表、提示文字、分配与实际动作的归档，全部用脚本化的假客户端检查。这些是接口见证，不是真实模型的行为或效果样本。
- 本机不可验证：真实模型在强制请求下能否绑定合法参数、之后能否完成复核与答复；集成测试与 `test_no_leakage.py` 需要云端数据。
- 本轮全部回合属于同一基础任务、同一实现、同一故障谱系，且共享同一段前缀，是开发观察，不构成独立样本，不报告比率或区间。
- 撤回方式：还原本轮对上述三个代码文件的提交即可，归档与评分不受影响。
